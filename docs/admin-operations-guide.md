## 一、系統怎麼運作（整體邏輯）

> 完整規格見 [Church_Parking_Management_System_PRD.md](Church_Parking_Management_System_PRD.md)；以下是給 admin 看的白話版。

### 1.1 車位怎麼算

地下室固定 **23 個車位**，但每週想停車的人可能有 40–50 台車，所以系統每週都要算出「這週實際能開放給一般會友申請的車位數」：

```
可分配車位 = 總車位（23）− 保留／停用車位 − 全職同工本週保留數
```

- **保留／停用車位**：外賓保留位＋當週故障或停用的車位，兩者合併成一個數字，在 [車位設定](#車位設定-admincapacity) 頁操作。
- **全職同工保留數**：**本週需要停在這 23 格裡的全職同工人數**——這個數字系統自動算，**Admin 改不動**。
  - ⚠️ **不是「本週有幾位同工來教會」。** 教會**另外自行控管一個停車區**給全職同工，那一區**完全不在這個系統裡**：本週停 0 台或停滿，都不會影響上面的公式。只有當某位同工**這一週需要改停這 23 格**（例如需要提早離開、不方便停自管區）時，才會從 23 格裡撥一格給他。
  - 例：某週 2 位同工需提早離開而改停這裡、另有 3 格保留／停用 ⇒ 可分配 = 23 − 3 − 2 = **18**。其餘同工照常停自管區，不影響這個數字。
- 這個公式**由系統原子計算並鎖住**：如果你想改的數字會讓「可分配」小於「本週已經核准的人數」，系統會直接拒絕（不會讓車位變成負的、超賣）。

### 1.2 誰優先停車（排序規則）

車位不是先搶先贏，而是照「關懷優先」排序：

| 等級 | 對象 | 說明 |
|---|---|---|
| **P1** | 全職同工／外賓 | 完全不進入排序，開放前就先扣掉名額 |
| **P2**（關懷優先） | 行動不便、孕婦、年長者同行、幼兒同行 | 需 Admin 核准過的資格；同一批 P2 之間再依「多久沒停到車」排序 |
| **P3**（一般會友） | 其餘所有申請人 | 先看違規分數（0–3，分數低者優先），再看多久沒停到車 |

P2 資格的核准／撤銷／到期追蹤走 [資格審查](#資格審查-admineligibility) 頁；每一種 P2 類型的細節（要不要每週宣告、效期多久）見 PRD 第五節。

### 1.3 一週的時間軸

```
週一 09:00 ── 開放本週申請（所有申請先進 pending 排隊）
週五 18:00 ── 系統自動分配：依排序規則核准，額滿的人進候補
              （之後仍開放「晚鳥」申請，隨到隨核准直到滿額）
週六 ────── 有人取消 → 候補依序遞補：
              18:00–23:59 取消 → 遞補者收到 LINE 通知，2 小時內要確認，
                                逾時或放棄則換下一位（原候補排位不變）
              週日 00:00 後取消 → 直接核准遞補者，不用等確認
主日 10:00–10:30 ── 現場點名開始
     10:20 ── 已核准但未到場的 P2 會友收到提醒通知（保留到 10:45）
     10:30 ── 一般會友（P3）未到場者，保留車位自動釋出；
              同時廣播通知候補者可到現場詢問同工
     10:45 ── P2 會友未到場（且沒回「正在路上」）者，保留車位釋出
              （回過「正在路上」的可延到 10:55）
              ── 10:30 後現場調度優先，不再保證依候補順位保留車位
Staff 結束點名 ── 整場沒出現、也沒取消的預約，結算為 no_show
```

### 1.4 取消不一定算違規

- **週五 18:00 前取消**：完全無記錄。
- **週五 18:00 之後、主日 10:30 前取消**：不計違規分數（系統理解是臨時狀況），並立刻觸發候補遞補。

### 1.5 No-show（完全沒來）的後果

- **一般會友（P3）**：沒來一次，違規分數 +1（上限 3 分），下次排序會往後；只要之後成功停車一次，分數就 −1。
- **P2 會友**：沒來**不扣分**（恩慈防護網），但系統會在 Admin 後台開一個「牧養關懷」提醒（不是懲罰，是提醒同工去關心會友近況），觸發時機是：
  - P2 會友連續 4 次沒來
  - 短期行動不便資格到了追蹤日期
  - 幼兒同行資格接近孩子入學年（系統依生日與台灣學年制 9/1 切點自動算出到期日，細節見交接文件，Admin 不需自己換算）

這些提醒都在 [牧養關懷](#牧養關懷-adminpastoral) 頁處理。

### 1.6 系統什麼時候會發 LINE 通知

依一週的時間順序：

| 時機 | 情境 | 通知內容（`template_key`） | 誰觸發 |
|---|---|---|---|
| **週五 18:00** | 分配核准 | 「○月○日主日的停車申請已核准」（`reservation_approved`） | 系統自動 |
| **週五 18:00** | 額滿進候補 | 「車位已額滿，您目前候補第 N 位」（`reservation_waiting`，帶名次） | 系統自動 |
| 週五～主日凌晨 | 候補遞補，需在期限內確認（**最長 2 小時，且不晚於主日 00:00**） | 「有一個車位釋出給您，請於 ○○:○○ 前確認」（`offer_2hr_confirm`，通知帶實際截止時間） | 系統自動 |
| 週五～主日 | 會友自己取消的確認 | `reservation_cancelled`（晚期取消另有文案） | 系統自動 |
| **主日 00:00** | 到期仍未確認的 offer 自動升為核准 | 「有名額釋出，已為您自動保留車位」（`offer_auto_approved`） | 系統自動 |
| **主日 00:00 後** | 此時才有人取消 → 遞補者**直接核准**，不用再等確認 | `reservation_approved`（同分配核准文案） | 系統自動 |
| 主日 10:20 | P2 到場提醒 | 「車位保留至 10:45；若正在路上，請開啟會友專區點『我正在路上』，可延長至 10:55」（`p2_arrival_reminder`） | 系統自動 |
| 主日 10:30 / 10:45 / 10:55 | 該次掃描**確實有車位被釋出**時，本人收到通知（資訊性、無罰責） | `reservation_released` | 系統自動 |
| 主日 10:30 / 10:45 / 10:55 | 該次**確實有釋出**時，**當下所有仍在候補的人**都會再收到一次廣播 | `broadcast_release`（現場先到先停、不保證保留） | 系統自動 |
| 主日現場 | 同工按「請車主移車」 | `move_car_request`（A 一般／B 緊急／C 散會後／D 車位調度，四種文案任選） | Staff 現場操作 |

> **10:30／10:45／10:55 不是「固定會發三次」**：那三個時間是釋出掃描執行的時刻，**該次真的有車位被釋出才會發通知**，一個都沒釋出就完全不發。也因此 `broadcast_release` 可能在同一個主日發出多次——每一層只要有人被釋出，就會對「當下仍在候補的人」再廣播一次。
>
> **回覆 LINE 訊息不會有任何作用。** 系統的 LINE webhook 只擷取綁定申請，不執行指令——所以上表任何一則通知都不會叫會友「回覆」，一律是「請開啟會友專區操作」。對會友解釋時請一致，否則他們會對著 LINE 打字然後石沉大海。
>
> `staff_reminder`／`admin_finalize_reminder` 兩個模板已寫好但**目前沒有任何排程會送出**，不列入上表。

所有通知都是**教會 LINE 官方帳號（OA）代發**、不會外露同工或其他會友的個人聯絡方式；前提是該會友已完成 LINE 綁定（見 [綁定審核](#綁定審核-adminbindings)）。通知的排隊與送出機制、健康度監控見 [通知系統狀態](#通知系統狀態-adminops) 頁與 [dispatcher-ops.md](dispatcher-ops.md)。

## 二、Admin 後台每一頁在做什麼

登入網址：`/admin`。左側選單（手機版在頂端橫向捲動）共 11 個功能，以下依「會友資料 → 車位/現場 → 監控/稽核」大致分組：

### 會友管理 `/admin/members`
搜尋會友（姓名／電話／車牌）、看完整明細（電話、車牌、資格狀態），對**未綁定 LINE** 的會友產生一次性綁定碼交給本人。列表搜尋結果電話會遮罩，明細頁才顯示完整資料。

> **會友資料維護（新增一位／改姓名手機／管理車輛）**：**既有會友的任何改動都在這裡做，不要用重新匯入。** 匯入是用手機號碼認人的，會友換號碼後重新匯入會把他變成**第二筆**會友資料（舊那筆才有 LINE 綁定與歷史），而**系統沒有合併工具**。
> - **新增會友**：頁面上方按鈕，不必為一個人做一份 CSV。名冊已有同名者時會先列出來請你確認是不是同一人。
> - **修改姓名／手機**（明細頁）：換手機號碼會**作廢該會友尚未審核的 LINE 綁定申請**（存檔後畫面會告訴你幾筆），請他重新在 LINE 送出一次；**已完成的綁定不受影響**。
> - **車輛**（明細頁）：新增車牌、**停用**（賣車／不再開）、**恢復使用**。停用不是刪除——紀錄保留、灰色顯示在下方，車牌釋出後可登記給別人。**車上還有未結束的預約時，系統會擋下停用**並告訴你有幾筆，請先處理該筆預約。
>
> 逐項操作說明與「為什麼不能用匯入改」，見 **[member-import-ops.md](member-import-ops.md) §3.5／§5**。

> **匯出 CSV（只有系統管理員看得到這個按鈕）**：一次下載全體會友名冊（姓名、**完整電話**、目前啟用車牌、角色、是否已綁定 LINE；不含資格事由與眷屬資料）。每次匯出都會寫進「稽核記錄」（誰、何時、幾筆）。**⚠️ 這是整批個資：檔案一旦下載就離開系統的存取控制與保留機制**——請只用於教會行政聯絡，妥善保管，**切勿上傳到公開雲端、貼到群組聊天或放在未加密的隨身碟／信箱**。幹事看不到此按鈕、也無法透過網址觸發。

### 名單匯入 `/admin/import`
把教會提供的會友 CSV（一般名單或 P2 資格申請表）上傳、預覽、確認寫入。**這是給非技術人員的頁面**，完整逐步說明＋每種錯誤訊息的意思，見 **[member-import-ops.md](member-import-ops.md)**。
> 匯入只建立會友資料，**不會**讓會友收到通知——收得到通知需要另外走下面的「綁定審核」。

### 綁定審核 `/admin/bindings`
把「已知會友」的 LINE 帳號正式對應到系統裡的人（寫入 `line_id`），之後移車/通知才送得到本人。兩種申請來源：會友自己在 LIFF 填「姓名＋手機」，或用同工發的一次性綁定碼。**一律人工核對後才核准**。完整流程＋各種拒絕原因的意思，見 **[binding-ops.md](binding-ops.md)**。

### 資格審查 `/admin/eligibility`
列出「已過期」「待覆核」「60 天內到期」的 P2 資格會友，點進會友明細頁可以核准、撤銷、或標記已覆核（並設定下次追蹤日期）。**「標記已覆核」之後，之後的 CSV 匯入不會再覆蓋你的決定**——這是刻意設計，避免幹事人工審過的資格被下一批名單匯入悄悄推翻。

### 車位設定 `/admin/capacity`
設定當週／下週（**只開放這兩週，不能設更遠的未來**）的「總車位」與「保留・停用車位」數字，畫面會即時算出「可分配車位」給你確認。系統會擋掉會讓車位變負或低於已核准人數的設定；若你剛好跟另一位同工同時在改，畫面會提示「已過期，請重新整理」而不是悄悄互相覆蓋。

### 列印點名表 `/admin/print`
列印當週點名表紙本，作為現場網路異常時的備援（Staff 頁本身是「唯讀快取」網路異常也能撐一陣子，但徹底離線時紙本是最後防線）。這是主日前辦公室的準備工作，不是主日當天在地下室操作的頁面。

### 現場 PIN 管理 `/admin/staff-pin`
幫當週／下週的 Staff（現場停車服事同工）發放登入 PIN 碼（6 碼數字，只顯示一次）。PIN 有效期會涵蓋到該主日結束，所以可以提前幾天先發。同一週重新發一組新 PIN，舊的會立刻失效。

### 帳號管理 `/admin/accounts`（只有系統管理員看得到）
管理**其他** Admin 帳號（不能對自己操作）：**新增管理者**（填帳號、選角色、拿一次性密碼）／變更角色（系統管理員 ⇄ 幹事）／停用／重啟／重設密碼／強制登出所有裝置。角色分兩級——**系統管理員**能用全部後台；**幹事**看不到帳號管理、通知系統狀態、稽核記錄這三頁。**建立系統管理員時會跳出高權限警告**，請確認對方真的需要那麼大的權限。系統保證永遠至少留一位啟用中的系統管理員，不會被誤操作歸零。新增第一位帳號或所有人都登不進去時的救援，仍走指令，見 [admin-account-ops.md](admin-account-ops.md)。

### 通知系統狀態 `/admin/ops`（只有系統管理員看得到）
先看一句白話結論（通知系統正常／異常）；下面「佇列數字與時間」「失敗通知重送」是可展開的技術細節（有幾筆等待送出、有幾筆失敗、失敗原因，異常時預設展開）。失敗過多時可以「死信重送」（先預覽、確認後才真的重送）。細節見 **[dispatcher-ops.md](dispatcher-ops.md)**。**幹事雖不能開這頁，但通知系統異常時，會在首頁「本週概覽」看到「通知系統異常，請聯絡系統管理員」的提示。**

### 牧養關懷 `/admin/pastoral`
處理系統自動開立的關懷提醒（P2 連續未到／資格到期追蹤）。處理時可選擇是否同時把「連續未到次數」歸零——這是關心不是懲罰，違規分數本身這裡不會被動到。

### 稽核記錄 `/admin/audit`（只有系統管理員看得到）
唯讀查看系統裡誰在什麼時候做了什麼異動（例如誰停用了哪個帳號、誰改了車位設定、誰把誰升成系統管理員），每一筆都會標出操作者**當時的身分**（系統管理員／幹事）。目前保存期是 24 個月，到期後由排程作業清除（見 [go-live-checklist.md](go-live-checklist.md) 1.5 的稽核清除 cron）。

## 三、日常維運節奏建議

| 頻率 | 該做的事 | 對應頁面 |
|---|---|---|
| 每主日前（週間） | 確認車位設定沒問題；如有新申請資格要核准，走資格審查 | 車位設定、資格審查 |

| 每主日後 | 看一次「通知系統狀態」有沒有異常失敗；有新綁定申請就審核 | 通知系統狀態、綁定審核 |
| 每次教會提供新名單 | 走匯入流程 | 名單匯入 |
| 每月 | 檢查稽核記錄清除 cron 有沒有正常跑（見 go-live-checklist 1.5） | 稽核記錄 |
| 不定期 | 有牧養關懷提醒就處理 | 牧養關懷 |

## 四、試營運怎麼做

> **這是目前教會最需要的部分**：開發已經全部完成，接下來是把真實會友資料、真實 LINE 官方帳號一步步接上，確認沒問題再全面開放。**唯一權威的順序清單是 [go-live-checklist.md](go-live-checklist.md)**——本節是給 admin 看的白話說明，實際勾選、驗證方式一律以該文件為準。

試營運的核心精神：**先讓少數人走完整流程、觀察至少一個主日沒出狀況，再逐步擴大**，而不是一次對全教會開放。

### 目前狀態（2026-07-29）

依 [go-live-checklist.md](go-live-checklist.md)：備份、正式 OA 接線、文案 sign-off、排程、開啟真實送出、**真會友名單匯入（2026-07-28，57 位）皆已完成**。**只剩最後一步：分批放行（Step 4）。** 實際勾選狀態請直接看該文件，不要以本文件的敘述為準（會隨時間過期）。

### Step 1：匯入真會友名單（1.3）
教會辦公室提供 CSV → Admin 走 [名單匯入](#名單匯入-adminimport) 頁 preview → 確認寫入。此時資料進系統了，但還沒人收得到 LINE 通知（因為還沒綁定）。

### Step 2：排程與稽核清除確認（1.5）
確認 11 個通知排程任務都正常指到正式網址，並新增每月一次的稽核記錄清除排程——`/admin/audit` 頁對外宣稱「24 個月後清除」，這句話要等這個排程真的在跑才算數。這步驟主要是技術/排程操作者（Scheduler operator）的工作。

### Step 3：開啟真實送出（1.6）
把系統從「模擬送出」切成「真的透過 LINE 送出」。切換前會先對**一位知情的操作者帳號**送一則測試通知，確認真的收得到，才繼續。

### Step 4：分批放行（1.7，最關鍵的一步）
1. **先找一個小組**（例如同工自己這一組），走綁定流程。會友端的完整白話步驟（含「一定要先加官方帳號好友」）在 **[member-binding-guide.md](member-binding-guide.md)**，可整份轉發給他們。兩條路徑：
   - **主要（自助）**：組員加官方帳號好友 → 從選單進會友專區 → 填姓名＋手機送出 → Admin 到 [綁定審核](#綁定審核-adminbindings) 頁核准。⚠️ **系統不會通知你有人申請，要主動去看這一頁。**
   - **備用（發碼）**：Admin 發一次性綁定碼給組員 → 組員在 LINE 傳「綁定 `<碼>`」→ 一樣到綁定審核頁核准。
2. **只對這個小組開放真實送出**（其他人維持不送，避免大範圍出錯）。
3. **觀察至少一個完整主日循環**：看 [通知系統狀態](#通知系統狀態-adminops) 頁的健康度——沒有異常失敗、沒有卡住的處理中列、未綁定的車主畫面上有正確顯示「無法通知」的提示。
4. **確認沒問題後才擴大到下一批**，重複「完成綁定 → 觀察一個主日 → 再擴大」直到全教會。（第二批以後同樣以**自助綁定為主**、發碼只是備用，不要回到 code-first。）

### ⚠️ 給試跑同工的說明（第一批放行前一定要講）

第一批試跑最可能出的狀況就是**通知沒送到**。這不是災難，但**事先沒講**就會變成災難——同工在現場乾等一則不會來的訊息。所以放行前務必對試跑的人講清楚下面三件事。

**1. 通知沒到，不代表你沒有車位——但請務必自己開會員頁確認一次。**
打開 LINE 裡教會官方帳號的選單 → 進入會員頁，上面就是你目前的狀態。**這一頁不經過通知系統**，所以通知壞掉時它照樣正確。然後看它顯示什麼：

- **「已核准車位」** → 位子已經是你的。車位是週五晚上分配時就寫進系統的，**通知只是把結果告訴你**；通知沒收到不會讓車位消失。
- **「已為您保留車位，請於 ○○:○○ 前確認」**（候補遞補到你）→ ⚠️ **這個有時限，一定要在畫面上的期限前按確認**。**過了期限，車位會自動釋出給下一位候補**——這種情況通知沒收到是真的會失去機會，所以試跑期間請養成主動看會員頁的習慣。
- **「候補中」** → 還在排隊，等遞補。

**2. 記住一句話：會員頁才是你的狀態依據，LINE 通知只是提醒。**
通知會漏、會晚、會因為沒綁定而根本送不出去；會員頁不會。**不確定的時候一律以會員頁為準。**

**3. 真的還是不確定，主日當天直接問現場停車同工。**
現場有一份**紙本點名清單**（Admin 從 [列印點名表](#列印點名表-adminprint) 印出來），那份是當天的依據。系統整個掛掉，靠這張紙也能把主日跑完——這正是第一批人數要少的原因。

**另外請試跑的同工幫忙回報**：什麼時候該收到通知卻沒收到、收到的內容看起來怪怪的、或畫面顯示跟實際不符。回報給 Admin（不用自己判斷是不是 bug）。**試跑的價值就在這些回報**，不是在「一切順利」。

> **給 Admin**：這段可以直接複製到 LINE 群組發給試跑同工。**不要**只說「有問題再跟我講」——沒講過第 1 點的人，收不到通知時會直接以為自己沒車位。

同時，[oa-onboarding-and-move-car-copy.md](oa-onboarding-and-move-car-copy.md) 有教會端「怎麼提高加入官方帳號比例」的具體做法（歡迎訊息、圖文選單、主日現場 QR code 等），這是讓分批放行能順利擴大的前提——沒加入 OA 的人，發了綁定碼也綁不了。

### 什麼時候算「正式營運」

當全教會的停車會友都完成綁定、真實送出穩定運作一段時間、[go-live-checklist.md](go-live-checklist.md) 全部項目打勾，就算正式營運，之後轉為第三節的「日常維運節奏」。

## 五、出狀況怎麼辦

- **通知送不出去 / 大量失敗**：先看 [通知系統狀態](#通知系統狀態-adminops) 頁健康度找原因（常見是會友沒綁定 LINE）。**已核准的車位不會因通知失敗而消失；但候補遞補的 offer 仍有確認期限、逾期會自動釋出給下一位**——請會友直接開會員頁查看目前狀態（該頁不經過通知系統），或看現場紙本點名表；試跑前的說明見上面「給試跑同工的說明」。需要緊急煞車時，停送通知屬於技術/排程操作者（Scheduler operator）權限，**做法是停掉外部排程器**（系統是被動等排程來觸發，沒有觸發就不會送）——**不要自行去改通知模式的設定**，那在正式環境會被系統拒絕、只是讓每次排程報錯。見 [go-live-checklist.md](go-live-checklist.md) 第 2 節 Rollback、[dispatcher-ops.md](dispatcher-ops.md)。
- **所有 Admin 帳號都被誤停用、沒人能登入**：這是設計上不該發生的狀態（系統會擋「停用最後一位」），萬一真的發生需要技術人員直接操作資料庫救援，見 [admin-account-ops.md](admin-account-ops.md)「真的卡住時」。
- **匯入中途出錯**：不用手動清資料，保留原始 CSV，重新跑一次「上傳並預覽 → 確認寫入」即可，系統設計成不會重複建立同一個人，見 [member-import-ops.md](member-import-ops.md) 第 4 節。
- **看不懂的錯誤訊息 / 結果跟預期差很多**：不要直接送出／確認，先截圖（只在你與開發者之間，不外流）聯絡開發者。
